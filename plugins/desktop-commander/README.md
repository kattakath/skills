# desktop-commander

Shell and filesystem tools that run **outside Claude Code's Bash tool**. That is the whole
reason this plugin exists, and it is a narrow one.

## The problem it solves

A worktree-isolated Claude Code session whose worktree has been **deleted** refuses every
Bash call — *"This session is isolated in the worktree … Refusing to run it there"* — and
spawned agents inherit the lock. The session can still think and still read, but it cannot
run a command, so it cannot dig itself out. This server's `start_process` is not the Bash
tool, so the guard never sees it.

**It is prophylaxis, not a rescue.** MCP servers are loaded at session start, so a session
that is *already* locked will not pick this up — it arms the next one. (And a restart, which
is what picking it up would require, resolves the lock by itself.) Install it before you
need it.

## It needs a companion on PATH

`.mcp.json` names a binary, not a package:

```json
{ "desktop-commander": { "command": "nix-mcp-desktop-commander" } }
```

That launcher comes from **`kattakath/nix-config`** — `modules/home/plugin-mcp.nix` builds
it when `local.pluginMcp.servers` includes `"desktop-commander"`. Same arrangement the
apify, wordpress and rag plugins have. Without it on PATH the server simply fails to
start, and nothing here can fix that.

Those three names are deliberately **not** in backticks, and neither is the one in the next
sentence. A backticked entry name inside a plugin's own markdown is how the skill-curator
plugin detects one entry depending on another (`skill-usage.py` greps for the name wrapped
in backticks), and it then marks the named entry `exempt` from staleness. So a prose
mention in backticks silently exempts an unrelated plugin from curation. Caught by that
suite's own `usage-cases.sh` on the first push of this plugin —
`FAIL rag: want active, got exempt`.

**Unlike those three, the reason the launcher is in Nix is not a credential.** This server
needs none. It is there because a plugin's `.mcp.json` cannot run
`sandbox-exec -f <profile>`, and that fence is the only thing that makes the server safe to
run at all.

## The fence is the OS, because the server says its own is not

Read at the source rather than from a summary:

- The README states `allowedDirectories` *"currently only restricts filesystem operations,
  not terminal commands"*.
- `SECURITY.md` states *"directory restrictions are guardrails, not sandboxing"*.
- `set_config_value` lets the **model** rewrite `allowedDirectories`, so an in-process
  restriction is one tool call from being lifted by the thing it restricts.
- `dist/tools/filesystem.js` returns **true for every path** when `allowedDirectories` is
  empty, and an empty list is also the fallback on any config error. The in-process check
  fails **open**.

So the launcher runs the server under a macOS Seatbelt profile generated by Nix. The profile
is a `/nix/store` path — unwritable by construction — and Seatbelt is inherited by every
process the server forks, which is what makes `start_process` safe to expose. The server's
own `config.json` is planted by Nix and its directory is write-denied, so
`set_config_value` cannot widen anything.

Measured 2026-10-07 on macOS 27, through these MCP tools: writes inside the allowed root
succeed; writes to the home directory, to `~/.zshrc` and to Claude Code's own `~/.claude`
fail `Operation not permitted`; reads of the operator's secret paths fail `EPERM`; `git`,
`gh` and `nix develop` all work normally.

## What the fence does NOT cover

Stated plainly, because the gap is the point of the tool. Routing around the Bash tool also
routes around every **Bash-text** rule in the operator's guardrails — `secret reveal`,
`security find-generic-password -w`, `agenix -d`, `git push --force`, `gh pr merge`. Those
have no filesystem component, so a filesystem sandbox cannot reproduce them and does not.
Keychain reads in particular go through `securityd` over mach IPC, so a file-read deny would
not stop them even in principle — and `git` and `gh` need them to work.

The fence covers the **file** axis only: where writes may land, and which paths may not be
read. Treat the rest as unguarded and keep the blast radius in mind when choosing to use
this server rather than Bash.

## The guard, and why it lives here

`hooks/hooks.json` registers a `PreToolUse` gate on this server's own tools
(`scripts/desktop-commander-guard.js`). It does two things of different strength:

- **Blocks** the command-text denies a filesystem sandbox structurally cannot express
  — printing a secret, decrypting an age file, a force-push without a lease, merging a
  PR. Seatbelt governs *where writes land*; it has nothing to say about these, and
  Keychain access goes through `securityd` over mach IPC where no file rule reaches.
- **Advises**, without blocking, that this server is the fallback: if Bash works, use
  Bash. A hard block there would be unfixable from inside a genuinely locked session,
  which is the one case this exists for.

It fails **open** on every error path. A bug in the guard costs supervision, never
availability.

**Why the plugin owns this rather than the operator's repo:** that repo's Bash guard
is registered with matcher `"Bash"`, so it is structurally never handed an MCP tool
call. Putting the mitigation in the plugin that introduces the capability also makes
it work in every repo, not just one.

**The inverted ancestor is worth knowing about.** The operator's repo previously
carried the *opposite* rule — a nudge pushing a bare `ls`/`find`/`stat`/`ps`/`kill`
*toward* this server, reasoning that tool preference was "not a safety concern". True
while this was one server behind a gateway; false once it became the deliberate way
around the Bash tool. It was also the only rule there with no test coverage, and it
is the one that silently inverted. Removed 2026-10-07; this guard points the other
way, and `tests/guard-cases.sh` is registered in CI so it cannot rot the same way.

## Two sharp edges

- **`set_config_value` hangs** under the fence rather than returning an error — the write
  cannot land, but the call never answers. Do not call it; the config is Nix-managed and is
  meant to be changed there.
- **Everything under the allowed root is writable, including the configuration repo that
  generates this fence.** An edit there needs an authenticated `darwin-rebuild` to take
  effect, so it is a review problem rather than a silent bypass — but it is not nothing.
